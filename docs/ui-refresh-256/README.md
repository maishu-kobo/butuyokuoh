# UI刷新 #256 — 比較と再現手順

推奨案は **C: 静かな日用品**。商品を探す検索を常設し、整列と細い区切りで操作の場所を安定させる。写真を楽しむAと、密な比較に強いBの中間として、登録・比較・購入予定を毎日使う場面に適する。半透明化や大きな装飾は使わない。

## 3案を試す

このディレクトリの `prototypes.html` をダウンロードしてブラウザで開く。HTMLだけで画像も含むため、サーバーやネット接続は不要。リポジトリのZIPでも開ける。上部のA/B/Cで同じ4商品を比較する。「スマホ幅」と「ダーク」で表示を切り替え、実機幅390pxと1280pxでも確認する。

| 案 | 構成 | 向く使い方 | 弱点 |
| --- | --- | --- | --- |
| A 編集カタログ | 写真の大小、セリフ見出し、非対称グリッド | 商品を眺めて選ぶ | 多件数の価格比較では走査量が増える |
| B 比較道具 | 小さな写真、密な行、価格と予定を隣接 | 候補を素早く比較 | 写真の魅力を伝える面積が小さい |
| C 静かな日用品（推奨） | 常設検索、整列、細い区切り、抑えた角丸 | 探す・追加・比較を繰り返す | Aのような誌面の個性は弱い |

試す順番:

1. 商品名検索、価格順、0件から検索を消す。
2. 商品を2件選択し「選択した商品を比較」。Tab/Spaceでも選択でき、フォーカスが残ることを確認する。
3. 商品名を押して購入予定日を保存し、「購入予定」を開く。
4. 「商品を追加」→URLを入力→確認→保存。
5. 「写真から」→サンプル写真または端末の写真→推定と未確定情報を確認→候補検索→選択→登録。
6. 写真検索の「失敗時を試す」から再検索する。ダイアログはEscapeで閉じられる。

**試作の操作はすべてモック。** 入力・画像は外部送信せずメモリ内だけで保持し、再読み込みで戻る。価格・店舗・予定は架空。写真は既存評価用画像4点で、HTML末尾に元URL・作者・利用条件を記載した。CC0/パブリックドメインの写真とCC BY-SA 3.0の写真が混在するため、再配布時は写真の表示クレジットとライセンスを保持する。実商品と価格の対応、写真判定の精度を示す資料ではない。

## 実アプリに適用した範囲

ヘッダー、画面切替、検索・並び順・絞り込みの表示にCの原則を適用した。検索と並び順は閉じたフィルターにも表示し、追加条件だけ折りたたむ。操作にはネイティブのボタン・ラベル・44pxの領域・明示的なフォーカスを用いる。新しいライブラリやフォントは追加していない。

実アプリのURL登録、写真登録、保存、比較、購入予定は従来のコンポーネントとコールバックに接続する。取得処理、商品カード、写真候補画面、推定/確定の文言、広告・出典・エラー表示は変更しない。**試作Cの全画面を移植した状態ではない**。商品カードの全面変更は一覧軽量化#36との競合を避けるため対象外とし、追加・写真画面の新しい配置も比較用試作に留める。

ベースは最新main `78161507701a4fc2f49919b8cb91cc3670a215c2` と同じツリーの検証基盤 `5e075aaf2ef4eb0dbbb97427d09bf3f1a967e99e`。写真登録の最新修正を含む。PRは `feature/capture-existing-bugfixes` 向け。main/developの更新、マージ、デプロイはしない。

## 調査した一次資料と採用理由

- [Apple HIG / Layout](https://developer.apple.com/design/human-interface-guidelines/layout): 重要度・整列・グループ化で階層を伝え、内容と操作を明確にする。Cの常設検索、一定の操作位置、狭い画面の折り返しに採用。Appleの素材は使用していない。
- [Things / Features](https://culturedcode.com/things/features/): リスト本体と補足操作の段階的な提示。絞り込みの詳細だけを折りたたむ理由にした。
- [MyRegistry / Help](https://customercare.myregistry.com/en/support/solutions/folders/48000658874/page/1?url_locale=en): 複数店舗の商品を一つのリストに置くサービスの情報整理を参照。商品名、価格、店舗、予定を比較可能にする。
- [Nielsen Norman Group / AI Prototyping](https://www.nngroup.com/articles/ai-prototyping/) と [Vague Prototyping](https://www.nngroup.com/articles/vague-prototyping/): あいまいな入力や生成結果の反復では、実際の用途と情報階層が弱くなりやすい。全要素を同じカードにしない、実際の商品データ量で設計する、装飾より操作とエラーを先に具体化する方針にした。

既存Issue #218（追加フォームのコントラスト）、#224（カード操作）、#248（写真候補の登録操作）と照合し、個別修正を作り直さず横断する表示改善として#256を作成した。実画面を開いたデザイン監査は環境制限で未完了であり、上記はコードと資料に基づく設計判断。

## 再実行

通常の開発環境で `npm ci` 後、`npm test`、`npx tsc --noEmit`、`npm run lint`、`npm run build` を実行する。続けて `npx playwright test tests/e2e/home-navigation.spec.ts tests/e2e/ui-prototypes.spec.ts` を実行する。E2Eはテスト専用のローカル起動と固定応答を使う。画像はPlaywrightの各test outputへ保存する。既存CIのartifactは失敗時のみ・7日保持のため、成功時の画像を永続保存したとはみなさない。

ブラウザ確認ができた環境で、通常のリスト画面・追加・写真登録・比較・予定の操作と、light/dark・390/1280px・キーボード・焦点復帰を確認し、画像をPRへ追加する。それまでDraftのままにする。ユーザーの判断待ちはデザインの選択（Cを推奨）のみで、実装を止める承認待ちは設けていない。
